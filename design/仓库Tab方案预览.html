仓库 Tab · 快照查看功能

在底部导航（桌面为左侧栏）新增「仓库」入口，按仓库维度查看云端已有的快照。
下面三套方案共用同一套数据接口，差别只在信息组织方式。示例数据取自你 NAS 上真实的两条任务（相册资料→天翼、115）。

对比项 方案 A · 分层（仓库 → 任务 → 快照） 方案 B · 扁平（仓库内全量时间线） 方案 C · 双栏（左仓库 / 右快照）
信息结构 三层：仓库卡 → 任务分组表 → 快照行 两层：仓库 chip → 全量快照列表（任务用色标区分） 两层：左侧仓库列表常驻，右侧直接是快照表
最接近你给的参考图 是（分组表 + 分页 + 操作列） 否（改成时间线） 是（表结构一致）
「一条快照属于谁」 分组标题直接表达，零认知成本 每行带彩色任务标，需扫视 列形式呈现，可排序/筛选
任务多时（>5） 页面变长，需折叠分组 不受影响，一屏看完 需要任务筛选器
手机端 卡片式，天然适配 列表式，最省空间 需退化为「卡片 + 抽屉」
实现成本 低 低 中（桌面双栏 + 手机抽屉两套布局）
建议 主推 可作为 A 的「时间线视图」开关 仓库数量多时再考虑
方案 A · 仓库 → 任务 → 快照（分层）推荐

第一层是仓库卡片，点进去是仓库详情：顶部汇总条 + 按备份任务分组的快照表。分组标题即「这是谁备的」，不用额外加列。

三套方案共用的实现要点

不管选哪个，底层是同一套东西，所以换方案只影响前端，返工成本很低。

1新增接口 GET /api/repos/:id/snapshots：返回该仓库全量快照 + 每条快照归属的任务 id/名称。复用现有的 snapCache 缓存（10 分钟），加 ?refresh=1 强制实时查。
2归属判定要改：现在 restic backup 没打 tag，快照和任务的关联只能靠源路径前缀匹配，两个任务路径重叠时会串。建议备份时加 --tag task:<id>，读取时 tag 优先、paths 兜底，历史快照不受影响。
3「保护」标记：restic 没有快照锁。若要做，就在本地 config 里维护一个 protected_snapshots 数组（repo_id + short_id），保留策略清理时跳过。不做就把这列删掉，只留任务和文件数。
4浏览：直接复用现有还原向导的文件浏览（/api/tasks/:id/files?snapshot=&dir=），点「浏览」跳到只读文件树，不进入还原流程。
5还原：点「还原」直接打开还原向导并预选这条快照，跳过前两步。
6性能：快照列表必须读缓存，不能每次实时 restic snapshots——天翼那 8 个快照实时查要十几秒。首次进仓库页用缓存，手动点刷新才实时查。
7入口：桌面左侧栏加第三项「仓库」，手机底部导航变三项。备份页的 FAB 在仓库页隐藏（没有「新建仓库」这个动作）。
我的建议：选 方案 A。它跟你给的参考图结构一致（表 + 分页 + 操作列），分组标题天然表达了「这条快照是谁备的」， 手机端也不用另做一套布局。如果你更关心「最近这个仓库发生了什么」，可以之后在 A 的详情页加一个「时间线 / 分组」视图开关，把 B 吸收进来。
